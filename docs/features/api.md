# Public API

A company can connect its own platform to prepza through the public API: list its interviews, invite candidates, read their results, and hear when a candidate finishes through a web hook. The reference is on the site at `/api-docs` (linked in the footer), read from the API's own OpenAPI description, so it always matches it.

## Keys

- An owner or admin makes a key on the company's **Integrations** tab → **API** → **API keys** → **New key**: a name, when it expires (in 1, 3, 6 or 12 months, or never; "never" shows a warning that a leaked key stays usable until deleted), and what it may do ([Permissions](#permissions)).
- The key (`pz_...`) is shown once. prepza keeps only its SHA-256 hash and its first characters, to tell keys apart.
- A key belongs to one company and acts as the member who made it: invites go out under that member's email limits. It stops working when it expires, when it's deleted, or when that member is no longer an owner or admin there (`401`; the api service rechecks that at most once a minute per instance).
- A company can have up to 10 keys, and all its keys together can make 60 requests a minute (`429` over it, with `Retry-After`: the seconds until the minute ends); these are the defaults of `MAX_API_KEYS` and `API_REQUESTS_PER_MINUTE`, which a superadmin can change ([Admin zone](admin-zone.md#limits)). Keys and web hooks are added one at a time per company (a Postgres advisory lock), so two added at once can't pass the limit. If Redis is down, requests go through without the limit rather than failing (logged).
- Deleting the company deletes its keys and web hooks; deleting an account deletes the keys and web hooks that member made.
- A key with the **mcp** permission also signs an AI agent in to prepza's MCP server, on the same terms (see [AI apps over MCP](mcp.md#api-keys)).

## Permissions

Each key may do only what was ticked when it was made, so a key for a dashboard only reads and a leaked key can do as little as possible. The permissions (`app/constants/permissions.py`), by what they touch:

| Group | Permission | Routes |
|---|---|---|
| Interviews | `interviews:read` | `GET /interviews`, `GET /interviews/{id}` |
| | `interviews:create` | `POST /interviews` |
| Candidates | `candidates:read` | `GET /interviews/{id}/candidates`, `…/{candidate_id}`, `GET /candidates?email=` |
| | `candidates:invite` | `POST /interviews/{id}/candidates`, `…/resend` |
| | `candidates:change` | `PATCH …/{candidate_id}` (name, extra time) |
| | `candidates:delete` | `DELETE …/{candidate_id}` |
| Credits | `credits:read` | `GET /credits` |
| AI agents | `mcp` | Signing in to the MCP server (`/mcp`) |

- Over MCP (`mcp`), each tool needs one of these too (`services/assistant/app/constants/key_tools.py`): `get_updates`, what's new in the key's company, needs `candidates:read`, and tells low credits only with `credits:read` ([AI apps over MCP](mcp.md#whats-new-get_updates)).
- A new key starts with `interviews:read` and `candidates:read` ticked (`DEFAULT_PERMISSIONS`, which the API page's form starts from); at least one is needed.
- A permission that changes something comes with reading what it changes (`IMPLIED`): ticking `candidates:invite` ticks `candidates:read`, and the form keeps it ticked. The api service applies the rule and answers the groups, the implied reads and the defaults (`GET /manage`); the form only shows them.
- Each public route declares its permission (`needs()` in `app/auth.py`, beside the key's check), and the API docs name it on the route. A key without it gets `403` with `{"detail": "This API key doesn't have the <permission> permission.", "code": "missing_permission"}`. A test fails on a public route that declares none.
- **Narrowing only.** An owner or admin unticks permissions on a key's row (**Edit permissions**, `PATCH /manage/keys/{id}` with `permissions`), keeping at least one. Adding one is refused (`409`, "A key's permissions can only be narrowed; make a new key to add one."), so a leaked key never gains power: a new permission means a new key. The key is locked while it changes, and the change applies only while the new set is within the key's current one, so two narrowings at once can't add back what the other took. A narrowing that takes something away goes to the company's [action log](companies.md#action-log) as "Narrowed an API key's permissions", with the key's name, what was taken away and who did it.
- Keys made before permissions existed have every API permission but `mcp` (api migration 0005), so they work as before and their reach never grows.
- Web hooks have no permissions: they're added in the app and send what they send.

## The API

Everything is under `https://<domain>/api/v1`, with `Authorization: Bearer pz_...`:

| Route | What it does |
|---|---|
| `GET /interviews` | The company's interviews, newest first |
| `GET /interviews/{id}` | One interview |
| `GET /interviews/{id}/candidates` | Its candidates with progress, grade, pass, integrity signals, a link to their results and, until they finish, their invite link (`invite_url`, null once finished or expired), newest first |
| `GET /interviews/{id}/candidates/{candidate_id}` | One candidate, also with each section's grade (`sections`, from rounds' scorecard; null in lists, so a list makes no call per candidate) |
| `POST /interviews/{id}/candidates` | Invites a candidate by email, with an optional name (or sends the invite again), as the key's maker; credits are set aside as in the app. Optional `return_url` and `sign_in` (below) |
| `POST /interviews` | Makes an interview from a job description (`job_description`, optional `language`), as the key's maker, under the same limits as the app (companies' `interview_creation`); `ready` turns true when its questions are made (`interview.ready`) |
| `PATCH /interviews/{id}/candidates/{candidate_id}` | Corrects the candidate's `name` (empty: unknown) and gives `extra_time` (0, 25, 50 or 100 percent) before they start (`409` after); only the fields given change, all or none: when one is refused, neither is made |
| `POST /interviews/{id}/candidates/{candidate_id}/resend` | Emails the invitation again, as a reminder (an expired one comes back for 30 days); `409` for a candidate who finished, or one invited with `sign_in: false` |
| `DELETE /interviews/{id}/candidates/{candidate_id}` | Revokes an unused invite (its credits come back) or erases a candidate who started, as on the candidate's page (`candidate_changes.remove`, audited `via: "api"`) |
| `GET /candidates?email=` | The company's candidates invited with that email, in any of its interviews, newest first (at most 100; `sections` null, as in lists: companies answers with the rows in one call) |
| `GET /credits` | The company's credits: `available`, `reserved`, `candidates` they pay for, `low` |

- Lists take `offset` and `limit` (up to 100). To sync, they also take `updated_since` (items changed then or later, oldest change first) and `after` (the last item's id, a keyset on `(updated_at, id)`, `helpers/sync.py` in companies). Interviews and candidates carry `updated_at`, which a Postgres trigger sets on every update of their row (companies' migration 0045), so no write can forget it; a candidate's progress while answering lives in rounds and doesn't change it.
- Retries are safe without anything from the client (`services/idempotency.py`); clients never manage idempotency keys. Inviting: the candidate is the key (the interview and their email, lowercased): an address whose invite is still open (invited, undelivered or in process) or who finished is returned as they are with `200`, without another email or credits (companies' internal invite route with `resend: false`); an expired invite is sent again and a removed one invited anew (`201`). Creating an interview: the server derives the key from the API key, the route and a SHA-256 of the canonical body, and keeps the first result in Redis for 15 minutes (`RETRY_WINDOW_SECONDS`): longer than HTTP clients' timeouts and retry backoff, shorter than making the same interview again on purpose. An `Idempotency-Key` header an older integration still sends keeps working (24 hours, under the company and the key's SHA-256, with the request's fingerprint), out of the docs; the same key with a different request is refused with `422`. A retry while the first runs gets `409`, a failed request frees the key, and with Redis down the request just runs.
- The writes go to companies' internal routes (`routers/internal_api_changes.py`) as the key's maker, which reuse the app's own services, so the rules, limits, credits, audit log and events are the same.
- **Sending candidates from your own platform.** With `sign_in: false`, prepza sends no invitation or reminder emails. Your platform sends the candidate to the response's `invite_url`, and they take the interview without signing in to prepza: the link signs them in as a guest that belongs to that one invite (companies signs a Firebase custom token for the uid `guest-<invite id>`; library counts guests neither as sign-ups nor as users). Anyone with that link can take the interview, so it goes only to the candidate. With `return_url` (an https address on the company's verified website domain or a subdomain: `verified_domain`, which a superadmin approved; `422` otherwise, also while the company isn't verified), the finished page shows a "Back to {company}" button to that address, with `prepza_invite=<candidate id>` added. With `theme` (`light`, `dark` or `default`, the candidate's own), the candidate's pages show that theme in the company's colors for it ([Brand](companies.md#brand)); a `?theme=` on the link, or the SDK's `theme`, wins over it. A company's interview pages (invitation, shared test link, questions, finished page) never show prepza's header or footer, whatever the invite.
- **Embedding the interview.** A company's page shows a `sign_in: false` candidate's interview itself with the hosted script `https://prepza.ai/embed/v1.js` (`frontend/public/embed/v1.js`): `Prepza.embed({ element, url: invite_url, theme, title, onReady, onStart, onFinish, onError })` makes a frame of `/embedded/{token}?origin=<the page's origin>` (and `&theme=` when given), which shows the invitation and then the questions in place (`EmbedView`), and returns `{ destroy }`. The documented snippet loads the script `async` after a one-line stub (`window.Prepza = { q: [], embed }`) whose queued calls the script replays; a second copy of the script leaves the first `Prepza` (it carries `version: 1`); unknown options get a console warning. The frame posts `{source: "prepza", version: 1, type}` messages only to that origin: `ready`, `started`, `finished` (with `candidateId`, the candidate's id), `resize` (its height, a finite number, which the script sets, at least 640 px) and `error` (`code`: `invite_unavailable` when the invite reads as gone, `load_failed` otherwise; `InviteView`'s `onUnavailable`). No `ready` within 20 seconds (an iframe never reports a refused load) is `onError({ code: "timeout" })`. The script is served with `Cache-Control: public, max-age=300, stale-while-revalidate=86400` and `Access-Control-Allow-Origin: *` (`EMBED_SCRIPT_HEADERS`, `next.config.ts`), and the proxy skips `/embed/`, so it loads as it is during maintenance too. Within v1 only additions; the docs give integrators the CSP lines and say not to pin it with SRI. Only the company's site may frame it: the page's `frame-ancestors` is the company's verified website domain and its subdomains (companies' invite view gives `embed_domain`, its `verified_domain`, for a guest invite only, `proxy.ts` reads it per request), `'none'` on every other page; so the site's pages carry no `X-Frame-Options` (the gateway and the load balancer keep it on the API). Inside a frame the guest's Firebase sign-in stays in memory (`lib/firebase.ts`), not in the frame's partitioned storage, which stalled it in WebKit; reloading the frame starts again from the invitation. Clicking outside the frame counts as leaving the page; the invitation's privacy link opens in a new tab. The docs page shows the snippet, from the API's description (code blocks in `lib/openapi.ts`).
- Companies' refusals pass through as they are: `402` without credits, `409` while the interview's questions are being made or when the company has as many interviews without candidates as it may, `422` for a `return_url` off the company's website, `429` over the email limits or the interviews a company or its key's maker may make a day, `503` while invites or interviews are paused or today's AI budget is used up (both with `Retry-After`), `404` for another company's interview.

## Web hooks

- An owner or admin adds up to 5 HTTPS addresses on the API page's **web hooks** tab. Like a key, a web hook works while whoever added it is still an owner or admin of the company; after that it gets nothing, its pending retries are dropped, its row says it stopped (checked on each load), and the first event it misses sends the company a `webhook_stopped` notification, once (`stopped` on the web hook). It works again if that member is made an owner or admin again. An address must lead to the public internet: prepza refuses private, loopback and link-local addresses when it's added and again before each send, then connects to the very address it checked (with the host's name for TLS and the `Host` header), so a lookup that answers differently the second time can't lead the send elsewhere. It never follows redirects, and never logs a web hook's address, which can carry a secret.
- Each web hook gets a signing secret (`whsec_...`), shown once and stored encrypted with `API_ENCRYPTION_KEY`.
- Events: a candidate started, finished, wasn't reached or expired (companies' `candidate.started`, `candidate.finished`, `candidate.undelivered`, `candidate.expired`, each saved with the change that caused it, `storage/candidate_events.py`) sends every web hook `{"interview", "candidate"}` as they are when it's sent, read from companies; a removed candidate (`candidate.removed`) sends `{"interview_id", "candidate_id", "email"}` from the event, as the candidate is gone; an interview whose questions are ready (`interview.ready`) sends `{"interview"}`. Every web hook gets every type (`services/webhooks.py` `send`); events companies saved before these fields existed are skipped. The api subscription takes every `candidate.` event and ignores the ones it doesn't send. When a candidate finishes, each web hook gets `POST {"id", "type": "candidate.finished", "occurred_at", "data": {"interview", "candidate"}}` (the developer docs show each event's body this way, `schemas/webhook_events.py`), the same objects the API returns, with `Prepza-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>">`. A candidate's results never change after that: a fixed question applies only to candidates who start after the fix, so there's no later event for a finished candidate.
- Delivery: all of a company's web hooks are sent to at once, each with 10 seconds in all to answer `2xx`. Only the answer's status is read, never its body, so an endpoint that answers gigabytes or a byte at a time can't hold the service. A web hook that took the event is remembered (`webhook_deliveries`, for 30 days), so a redelivered event reaches only the ones that failed. An event can arrive more than once; its `id` stays the same, and receivers are told to ignore repeats by it. Two sends of one event at the same time (a redelivered event while the retry job sends it) aren't prevented: both may arrive.
- Retries: an event a web hook didn't take is kept for it (`webhook_retries`), and the Pub/Sub event is done, so one company's failing endpoint doesn't hold up events for everyone. The `webhook-retries` job (every 5 minutes) sends it again after 5 minutes, then twice as long each time, at most 6 hours apart; each run sends 25 at once, batch after batch, starting none 40 seconds into the run (`RETRY_RUN_SECONDS`), and two runs never send the same one. It's dropped when it gets there, when whoever added the web hook is no longer an owner or admin, or after 3 days of failing: then the web hook is paused (`failing`, shown as paused in the API page's list). A paused web hook gets no events and its other retries go, so a dead endpoint costs nothing, until a test event sent from the API page goes through.
- A candidate the company erases (`candidate.removed`) has their results waiting to be sent again deleted from every one of the company's web hooks, so an erased candidate's data stops going out at once.
- A candidate also carries `flagged` (the integrity verdict the ATS gets), `extra_time` (percent per question), `started_at` and `finished_at` (companies keeps them since migration 0044, from the first start and the finish; earlier candidates have none).
- Every event body has `occurred_at`: when the change happened, the outbox row's time, which the outbox sends as a Pub/Sub attribute (`OCCURRED_AT_ATTRIBUTE`, the same on every re-send; events from before it fall back to Pub/Sub's publish time). A retried event can arrive after a later one, so clients order by it.
- Testing and the delivery log: on each web hook row of the API page, owners and admins **send test event** (`POST /manage/webhooks/{id}/test`, a signed `test` event sent at once, at most 30 a company an hour by default, `WEBHOOK_TESTS_PER_HOUR`, `429` past it, the answer saying whether it was taken), and every member opens its **delivery log** (`GET /manage/webhooks/{id}/log`): its latest 20 sends (`webhook_attempts`, `WEBHOOK_LOG_KEPT`), each with the event's type, when, whether it was taken and what happened ("delivered", "skipped", the status answered, or the error's name), no candidate's data.
- A web hook whose address no longer leads to the public internet is skipped. One whose secret can't be read (its key gone from `API_ENCRYPTION_KEY`) counts as a failed send, logged "secret unreadable" (the delivery log says "Not sent: a problem on prepza's side.") and retried, so it shows as failing and its events go out once the key is back. An address whose lookup fails counts as a failed send and is retried. A candidate or interview deleted since is told to nobody; if the companies service can't answer for now, the event fails and Pub/Sub retries it, and nothing has been sent yet.

## In the action log

A key created, deleted or narrowed, and a web hook added, tested or deleted, go to the company's [action log](companies.md#action-log) as the member's, named by the key's name or the web hook's site only (its path can carry a secret). Api saves each in its outbox in the change's own transaction (`prepza_common.audit.add`, event `audit.recorded`), publishes it right after the request and every minute (`api-outbox`), and companies stores it once.

## The API page

`/companies/<id>/integrations/api`, from the **API** row on the integrations tab (which shows how many keys and web hooks the company has):

- Two tabs, **API keys** and **web hooks**, each a list with its own button in the title row (**new key**, **add web hook**) for owners and admins, next to **developer docs**.
- A key shows its first characters, when it was made, when it expires (or that it expired), when it was last used (noted at most once a minute), and its permissions, one group a line. Owners and admins narrow them from the row ([Permissions](#permissions)). Viewers see the lists without the buttons, and each web hook's address only up to its site (`https://hooks.zapier.com/…`): the rest of a Zapier or Make address works like a password.

## How it's built

- The `api` service (`services/api`) owns the keys, web hooks, deliveries and retries in its own database. It has no business rules of its own: interviews, candidates and invites come from companies' internal routes (`/internal/companies/{id}/interviews/...` and `/internal/interviews/{id}/invites`).
- It's reached at `/api/v1/` (the gateway locally, the load balancer's `v1` path in Google Cloud). The management routes (`/api/v1/manage`, for the API page, signed in with Firebase) and the internal ones are left out of the public OpenAPI.
- `POST /internal/keys/verify` checks a key for the assistant's MCP server exactly as the API does (the same expiry, maker and rate-limit checks, counted against the company's API limit) and answers its id, company, maker and permissions.
- It consumes companies' `candidate.*` events and `interview.ready` (web hooks) and `company.deleted` (deletes the company's keys and web hooks).

## Settings

| Setting | What it does |
|---|---|
| `API_ENCRYPTION_KEY` | The Fernet key that encrypts web hooks' secrets. Empty: keys work, but web hooks can't be added ("Web hooks aren't set up yet") and none is sent. Keep it: a new key makes every web hook unreadable, so they have to be added again. To replace it, list the new key and the old one, comma-separated, new first (see [infra/README.md](../../infra/README.md), step 8) |
