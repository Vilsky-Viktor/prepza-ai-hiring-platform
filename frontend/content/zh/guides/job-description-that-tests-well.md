# 如何写出便于技能测试的职位描述

职位描述有两项任务。它向求职者说明这个岗位是什么，也是你之后所有考察的起点：简历筛选、技能测试、面试问题。职位描述写得含糊，后面的每一步都只能去猜这份工作需要什么，而根据它生成的技能测试最终考的就是这种猜测。

本指南讲的是第二项任务：写出一份可以据此生成技能测试的职位描述。它写给招聘经理和招聘专员，无论你使用什么工具。同样的习惯也会让招聘广告更清楚。

## 为什么职位描述决定了测试

知识测试只有在考察工作真正需要的内容时才有用。招聘研究把岗位知识测试列为平均而言较能预测工作绩效的方法之一，但这一估计针对的是为该岗位专门编写的测试；与岗位无关的知识测试预测力更弱（参见[技能测试与简历筛选对比](/guides/skills-tests-vs-cv-screening)）。

美国的雇佣法规从法律角度表达了同样的意思。《雇员甄选程序统一指南》（Uniform Guidelines on Employee Selection Procedures）要求，以内容为依据的测试应建立在岗位分析之上，而且这项分析应聚焦于“工作行为以及与之相关的任务”（[29 CFR 1607.14(C)](https://www.law.cornell.edu/cfr/text/29/1607.14)）。在实践中，对大多数团队来说，职位描述就是写成文字的岗位分析。此外，根据《美国残疾人法》（ADA），在发布招聘广告或面试之前准备好的书面职位描述，被视为一个岗位基本职能的证据（[42 U.S.C. 12111(8)](https://www.law.cornell.edu/uscode/text/42/12111)）。

所以，职位描述值得多花半小时。它写了什么，测试就会考什么。

## 好的职位描述能为测试提供什么

### 1. 具体的技能、工具和概念

写明完成这份工作必须掌握的内容，用测试能够出题的说法来写。

| 难以测试 | 可以测试 |
| --- | --- |
| 扎实的财务背景 | 能做银行对账，熟悉增值税规定，能在总账中录入会计分录 |
| 数据驱动思维 | 能编写包含连接和聚合的 SQL 查询；能用 Power BI 搭建看板 |
| 出色的客户服务能力 | 按公司政策处理退款和投诉；会使用 Zendesk 宏和升级规则 |
| 现代 Web 开发 | 能用 Hooks 编写 React 组件；能调用 REST API；能用 Jest 编写单元测试 |

当具体工具或标准很重要时，就写出它的名字。“财务软件”等于让测试自己挑一个；“Xero”则不会。如果几种工具中任何一种都可以，就直接这么写（“PostgreSQL 等关系型数据库”），并预期测试考的是这类工具，而不是清单上的每一个名字。

### 2. 级别

同一个主题，可以考得深浅差别很大。初级分析师应该知道连接（join）的作用；高级分析师应该知道查询为什么慢、该改什么。写明你需要哪一种：

- **职责范围：** 哪些事情可以独立决定，哪些要交给别人。
- **复杂程度：** 常规情况，还是少见情况和权衡取舍。
- **资历：** 初级、中级还是高级，写在职位名称或正文里。

工作年限只是级别的粗略替代，而且是很弱的一种：在上文提到的研究中，它是预测工作绩效最弱的指标之一。如果要写，也请写清楚这些年限应该让人能胜任哪些工作。

### 3. 日常工作内容

对测试最有用的是岗位职责。“编制每月增值税申报表”或“对新提交的 bug 进行分类并复现”能告诉出题人会用到哪些知识、在什么场景下用到。职责用“动词 + 对象”来写，就像向新同事介绍工作那样。

如果不确定某个岗位通常做什么，[O*NET OnLine](https://www.onetonline.org/) 列出了数百种职业的典型任务、技术和知识。把它当作检查清单，然后只保留你的岗位实际要做的部分。

### 4. 明确区分必备要求和加分项

考察加分项的测试，会因为一个月就能教会的东西把人筛掉。确定哪些技能是第一天上岗就需要的，其余的要么清楚标出，要么不放进用来生成测试的文本。

团队打算在岗培训的知识，根本不应出现在筛选测试中。《统一指南》指出，以内容为依据的测试不适用于“预期雇员将在工作中学习”的知识（[29 CFR 1607.14(C)(1)](https://www.law.cornell.edu/cfr/text/29/1607.14)）。

## 哪些内容不该写

有些内容对招聘广告有帮助，对测试却毫无用处。还有些内容根本就不该出现。

- **描述性格和态度的词：** “主动自驱”“大牛”“有激情”。这些无法用知识题来考察，而且往往读起来像在描述一类人，而不是一份工作。
- **企业文化、福利和口号。** 愿意的话可以留在广告里；它们不是测试素材。
- **硬性条件：** 证书或执照、工作许可、语言、可到岗时间。这些是简历筛选阶段“是或否”的核查项，不是要测试的知识。
- **会劝退某些人群的措辞。** 美国 EEOC（平等就业机会委员会）举过一个例子：招聘广告寻找“女性”或“应届毕业生”，“可能会让男性和 40 岁以上的人不敢申请”，并可能违法（[EEOC](https://www.eeoc.gov/prohibited-employment-policiespractices)）。欧盟和英国也有类似规定。描述工作本身，而不是你想象中做这份工作的人。
- **公司所做的一切。** 一段关于这个岗位根本不会接触的产品的介绍，可能最终变成一个测试主题。

## 公开的招聘广告和用于测试的文本可以不同

招聘广告要把岗位推销出去；测试只需要岗位要求。如果你的广告很长，不必用全文来生成测试。粘贴要求和职责，再加一句说明级别，其余的都可以省掉。用 15 行精确的文字生成的测试，通常胜过用三页文字生成的测试。

## 示例

**修改前：**

> 我们正在寻找一位拥有 5 年以上经验、热爱数据的大牛级数据分析师。你将与我们超棒的团队一起，使用前沿工具（SQL、Python、BI 工具等）参与激动人心的项目。优秀的沟通能力和成长型思维是必须的。免费午餐，办公室可带狗！

根据这段文字生成的测试只能去猜：什么级别、哪种 SQL、哪款 BI 工具，以及“激动人心的项目”具体做什么。一半的文字都无法测试。

**修改后：**

> **数据分析师（中级）。** 独立完成常规分析，与高级分析师合作搭建新模型。
>
> - 在 PostgreSQL 中编写 SQL：连接、聚合、窗口函数、慢查询的执行计划
> - 为销售团队搭建并维护 Power BI 看板
> - 用 Python 和 pandas 清洗和合并数据
> - 定义并核查指标：转化率、留存率、同期群分析
> - 以书面形式和简短会议向非技术背景的经理汇报分析结论
>
> 加分项，不纳入测试：dbt、电商行业经验。

每一行都写出了可以出题的内容，级别写明了，加分项也做了标注。

## 生成测试前的检查清单

- 每项技能写的是工具、方法或概念，而不是性格特质。
- 写明了级别：资历、可以独立决定什么、处理的情况有多复杂。
- 职责以“动词 + 对象”的形式书写。
- 必备要求和加分项清楚分开。
- 不包含你打算在岗培训的内容。
- 硬性条件留给简历筛选。
- 没有描述你想象中那个人的措辞，只描述工作。

## prepza 如何使用职位描述

prepza 是根据职位描述生成限时选择题技能测试的工具之一。下面介绍它如何处理这段文字，让你看到上述建议在实际中如何发挥作用：

- **它会读取每一项要求。** AI 从每个部分中挑出每一项技能、工具、概念、资质和日常职责，包括标为“优先”或“加分项”的内容。企业文化介绍、福利和口号会被排除。
- **可互换的示例合并为一项。** “A、B 或类似工具”会作为一类工具保留，并以文本优先提到的那个（或使用最广泛的那个）作为示例。用“和”连接的各项则分别保留。所以，如果你需要的是某一个特定工具，就只写那一个。
- **年限和性格特质会被去掉。** 工作年限、资历、积极性之类的说法无法测试，因此只使用它们所指的技能。
- **级别来自文本。** 职位描述要求的资历、工作年限和职责范围决定测试的级别：初级、中级或高级。级别决定题目考察的深度和每道题的默认时间：初级或中级为 60 秒，高级为 75 秒（参见[技能测试如何设置时间](/guides/skills-test-timing-and-extra-time)）。
- **在编写任何题目之前，由你批准主题。** 要求会被整理成最多 10 个主题，每个主题最多 5 个子主题。你可以取消勾选某个主题、重命名它、编辑它的子主题，或用普通文字描述修改（“去掉 dbt”）。混进来的加分项可以在这里轻松删掉。
- **然后每个主题会有自己的题库，** 每位候选人从中随机抽到一组题目。

你最多可以粘贴 10,000 个字符，也可以只用一两句话描述这个岗位。没有任何可测试内容的文本，比如菜谱或闲聊，会被拒绝。一份简短的技能清单也可以，但写明级别和日常工作的职位描述能生成更好的主题。

想试试的话，在首页粘贴一份职位描述，或者从[按岗位分类的技能测试](/tests)中选一份现成的测试开始。
