# 如何招聘工程师：从职位描述到发放 offer 的结构化招聘流程

招聘工程师的成本很高，而且高在一个容易被忽视的地方：大部分成本是你自己工程师的时间。他们每花一小时去面试一个并不熟悉你们技术栈的人，就少了一小时做开发。好的流程会把便宜、覆盖面广的检查放在前面，把昂贵、深入的考核留给少数很可能成功的人。

本指南会一步步讲解这一流程。在研究结论明确的地方，我们引用招聘研究；在结论不明确的地方，我们也会如实说明。

## 流程一览

| 阶段 | 考察什么 | 谁投入时间 |
| --- | --- | --- |
| 1. 岗位画像与职位描述 | 这份工作真正需要什么 | 招聘经理、一位资深工程师 |
| 2. 简历或申请筛选 | 仅限硬性要求 | 招聘专员或招聘经理 |
| 3. 知识笔试 | 候选人对你们技术栈的了解 | 候选人；你只需查看结果 |
| 4. 带回家的作业或现场编程 | 能否写出可运行的代码 | 一到两位工程师 |
| 5. 系统设计（高级岗位） | 如何思考更大规模的系统 | 一位资深工程师 |
| 6. 结构化行为面试 | 如何与他人协作 | 招聘经理、一位同级同事 |
| 7. 背景调查 | 核实你已了解到的情况 | 招聘经理 |
| 8. 决策与发放 offer | 公平且有记录的决定 | 招聘团队 |

## 研究怎么说

大型招聘研究综述会按照各种方法的结果与日后工作绩效的相关程度来比较它们。最近一项重要研究由 Sackett、Zhang、Berry 和 Lievens 于 2022 年发表，它下调了早期的估计值，并发现平均而言预测力最强的方法都是与具体岗位相关的测评（[doi:10.1037/apl0000994](https://doi.org/10.1037/apl0000994)）。他们的估计值如下，0 表示毫无关联，1 表示完全相关：

| 方法 | 估计效度 |
| --- | --- |
| 结构化面试 | .42 |
| 岗位知识测试 | .40 |
| 工作样本测试 | .33 |
| 非结构化面试 | .19 |
| 工作年限 | .07 |

由此可以得出三点适用于工程师招聘的启示：

- **结构比形式更重要。** 同样的面试，如果有固定问题和评分指南，预测效果远好于一场非结构化的聊天。
- **工作年限本身说明不了太多。** 与一个人实际掌握的知识和能力相比，“五年 Java 经验”只是一个很弱的信号。
- **组合使用多种方法。** 没有任何一种方法的预测力强到可以单独使用。

这些是跨越大量岗位和研究的平均值，并不能保证适用于你的岗位。作者还指出，知识测试和工作样本适合那些预期候选人已经受过培训或具备经验的岗位。大多数工程师招聘符合这一点，但学徒岗位并不符合。

## 第 1 步：写清楚岗位画像和职位描述

在发布任何内容之前，先写下这个人入职前六个月要做什么，以及第一天就必须掌握什么。要具体：

- **必须掌握：** “能编写和审查 PostgreSQL 查询，包括 join 和索引”是可以考察的；“数据库能力强”则不行。
- **入职后再学：** 你们的内部工具、业务领域，以及你们会教的那部分技术栈。
- **级别：** 在你的团队里，中级和高级的区别是什么，例如端到端负责一个服务，或主导设计决策。

与所有参与这次招聘的人就此达成一致，然后据此撰写职位描述。与实际工作相符的职位描述能吸引合适的人，也让后续每一步更容易安排，因为每一项测试和面试都能追溯到它。

“加分项”要写得简短。冗长的要求清单会把那些没有逐条满足、但其实合格的人拒之门外。

## 第 2 步：简历筛选只看硬性要求

用简历或申请表做“是或否”的检查：工作许可、岗位需要时的所在地或时区、必需的语言能力，以及这份工作确实缺一不可的条件。

不要根据简历给人排名。职位头衔、雇主名称和工作年限都是很弱的预测指标，而且简历很难公平比较：一份出色的简历既可能反映出色的工作，也可能只是反映出色的文笔。把简历当作筛选那些无法通过测试考察的条件的工具，所有通过的人都进入知识笔试。

## 第 3 步：进行一次简短的知识笔试

这一步最能节省工程师的时间。在任何人花一小时参加现场面试之前，先检查每位候选人对你们技术栈的了解程度。

一场好的知识笔试应该：

- **针对岗位：** 考察岗位画像中的编程语言、框架、数据库和工作实践，而不是泛泛的冷知识。
- **简短：** 几个主题，每个主题约 10 道题，这样手握其他 offer 的优秀候选人也愿意完成。
- **人人相同：** 相同的主题、相同的题量和相同的时间限制。

这正是 testee 的用武之地。它会把你的职位描述变成一场限时选择题知识面试。在生成任何题目之前，你会先审核建议的主题，因此测试只覆盖你们的技术栈，不多也不少。对于工程岗位，这可以包括：

- **代码阅读题：** 给出一小段代码，问它会打印或返回什么、它做了什么、为什么出错，或者哪处修改能修复它。
- **SQL：** 给出一张小表和一条查询，问会返回哪些行。
- **架构和框架知识：** 权衡取舍、某个框架的行为方式、高负载下会出什么问题。

每位候选人会拿到自己的一组随机题目，每道题都有倒计时。你会看到一份评分卡，列出每个答案及其用时，并标记答题过快、离开页面、尝试复制的情况，以及答案和用时中的异常模式。标记只是值得仔细查看的理由，不能证明任何事情。报告还会推荐一些候选人答对的题目，供你在下一轮面试中追问。

testee 不做的事：候选人不会在 testee 中编写、运行或调试代码。读代码和写代码是不同的技能，所以下一步依然重要。可以从[按岗位分类的技能测试](/tests)中挑选现成的测试作为起点。

## 第 4 步：带回家的作业或现场编程

现在检查候选人能否写出可运行的代码。这一阶段考察编写、运行和调试代码，可以用你们自己的练习题，也可以用开发者测评平台。关于知识笔试和编程平台如何配合，请参阅 [HackerRank 替代方案](/compare/hackerrank-alternatives)。

两种常见形式：

- **带回家的作业：** 贴近实际、压力小，但会占用候选人的晚上时间。最多控制在几个小时内，说明预计需要多长时间，并用书面评分标准来评审。
- **现场编程：** 时间更短，也更难找人代做，但压力更大。围绕一个贴近实际的问题结对编程，让候选人使用最熟悉的语言，评判他们的思路，而不只是看是否完成。

无论哪种形式，都要按事先商定的标准打分：正确性、可读性、测试、如何处理边界情况。由于知识笔试已经筛选过一轮，这一步你只需面对少数几个人，而不是所有人。

## 第 5 步：高级岗位的系统设计

对于高级工程师，增加一场设计讨论：“你会如何构建一个实现 X 的服务？”关注他们如何澄清需求、如何在各种取舍之间做选择，以及如何发现故障点。这类问题很少只有一个正确答案，所以评分标准必不可少。在第一场面试之前，就写好弱、合格和优秀的回答分别是什么样子。

初级岗位可以跳过这一步，因为它在初级岗位上考察的主要是自信，而不是能力。

## 第 6 步：带评分标准的结构化行为面试

在 Sackett 等人（2022）的研究中，结构化面试是预测力最强的单一方法。结构化意味着：

- **每位候选人回答相同的问题，** 且与岗位画像挂钩：“讲一次你不同意某个设计决策的经历。你是怎么做的？”
- **每个问题都有评分标准，** 并附上弱、合格和优秀回答的示例。
- **独立打分：** 每位面试官先自己打分，再与他人讨论，这样结果不会被最响亮的声音左右。

这一阶段用来考察测试无法体现的方面：协作、主人翁意识、对待反馈的方式，以及与非工程人员的沟通。

## 第 7 步：背景调查

背景调查可以印证你已经了解到的情况，也能发现隐忧，但应把它当作最后的核实，而不是决定性的考核。Sackett 等人没有给出背景调查的效度估计，因为现有研究太少，所以几乎没有证据表明它能多好地预测绩效。如果要做，就向每位证明人问同样几个关于具体行为的问题。

## 第 8 步：候选人体验与发放 offer 的速度

优秀的工程师往往同时在走好几家公司的流程。缓慢或混乱的流程会让你失去他们。

- **一开始就告诉候选人完整流程：** 有哪些阶段、每个阶段需要多长时间、什么时候会收到回复。
- **保持流程简短。** 把后面几个阶段安排得紧凑一些，最后一场面试结束后尽快做决定。
- **尊重他们的时间。** 早期安排一场简短的知识笔试，就能让更少的人去参加那些他们本来就不太可能通过的长时间面试。
- **及时回复每一个人，** 包括没有进入下一轮的人。

## 全程保持公平

结构化的流程也更公平，但前提是你始终如一地执行：

- **问题一致：** 同一岗位的每位候选人，在每个阶段都回答一致的问题。
- **评分标准事先写好，** 让所有人按同样的标准接受评判。
- **合理便利：** 为提出需要的候选人（例如因残障）提供额外时间或其他形式。在 testee 中，你可以在候选人开始之前为其增加额外时间。
- **监测结果。** 不同方法在不同群体之间呈现的分数差距不同。Sackett 等人发现，岗位知识测试和工作样本的平均差异大于结构化面试，这也是应该组合使用多种方法的又一个理由。关注每个阶段的通过率。
- **由人做决定。** 分数是决策的依据，而不是决策本身。在拒绝任何人之前，先看看他们的答案。

关于法律基础知识，包括欧盟《人工智能法案》(EU AI Act) 和美国关于录用率的规定，请参阅[招聘前测评](/pre-employment-testing)。

## 总结

把覆盖面广、成本低的检查放在前面，把深入、昂贵的考核放在最后。用简历筛选硬性要求，进行一次简短的知识笔试，然后把工程师的时间花在剩下少数人的编程、设计和结构化面试上。按照事先写好的评分标准打分，并让流程快速、清晰。
