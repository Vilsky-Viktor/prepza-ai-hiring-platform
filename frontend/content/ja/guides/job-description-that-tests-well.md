# スキルテストに生かせる求人票の書き方

求人票には 2 つの役割があります。応募者にその仕事が何かを伝えること、そして書類選考、スキルテスト、面接の質問など、後で確認するすべてのことの出発点になることです。求人票があいまいだと、後の各ステップは仕事に何が必要かを推測するしかなく、そこから作ったスキルテストはその推測をテストすることになります。

このガイドで扱うのは 2 つ目の役割、つまりスキルテストを作れる求人票の書き方です。どのツールを使っているかに関係なく、採用責任者と採用担当者に向けた内容です。同じ習慣で、求人広告もわかりやすくなります。

## なぜ求人票がテストを決めるのか

知識テストが役に立つのは、仕事に実際に必要なことをテストするときです。採用研究では、職務知識テストは平均して職務成績をよく予測する手法の一つに数えられますが、この推定値はその職務のために作られたテストについてのものです。職務と関係のない知識テストの予測力はもっと低くなります（[スキルテストと書類選考の比較](/guides/skills-tests-vs-cv-screening)を参照）。

米国の雇用規則も、法的な面から同じことを述べています。Uniform Guidelines on Employee Selection Procedures（従業員選考手続きに関する統一ガイドライン）は、内容の妥当性に基づくテストが職務分析、それも「職務行動と、それに伴うタスク」に焦点を当てた職務分析に基づいていることを求めています（[29 CFR 1607.14(C)](https://www.law.cornell.edu/cfr/text/29/1607.14)）。実際には、ほとんどのチームにとって求人票がその分析を書き留めたものです。また、障害を持つアメリカ人法（ADA）では、求人広告や面接の前に用意された職務記述書は、その仕事の本質的な機能を示す証拠とみなされます（[42 U.S.C. 12111(8)](https://www.law.cornell.edu/uscode/text/42/12111)）。

ですから、求人票にはあと 30 分かける価値があります。求人票に書いたことが、そのままテストで問われるからです。

## よい求人票がテストに与えるもの

### 1. 具体的なスキル、ツール、概念

仕事をするために知っている必要があることを、テストで問える言葉で書きます。

| テストしにくい | テストできる |
| --- | --- |
| 経理・財務の豊富な経験 | 銀行勘定の照合ができ、消費税のルールを理解し、総勘定元帳に仕訳を計上できる |
| データドリブンな考え方 | 結合と集計を含む SQL クエリを書ける。Power BI でダッシュボードを作れる |
| 優れた顧客対応力 | 規定に沿って返金とクレームに対応できる。Zendesk のマクロとエスカレーションルールを使える |
| モダンな Web 開発 | フックを使って React コンポーネントを作れる。REST API を呼び出せる。Jest で単体テストを書ける |

重要な場合は、実際のツール名や規格名を書きます。「会計ソフト」ではどれを出題するかをテストに任せることになりますが、「Xero」ならそうはなりません。いくつかのツールのどれでもよい場合は、そうはっきり書き（「PostgreSQL などのリレーショナルデータベース」）、テストはリストの各ツールではなく、ツールの種類を扱うものと考えてください。

### 2. レベル

同じトピックでも、テストする深さは大きく変わります。ジュニアのアナリストなら結合が何をするかを知っているべきで、シニアなら、なぜクエリが遅いのか、何を変えればよいかを知っているべきです。どちらが必要かを書きましょう。

- **裁量の範囲：** 一人で決めることと、ほかの人に任せること。
- **難しさ：** 定型的なケースか、まれなケースや判断の難しいトレードオフか。
- **経験レベル：** ジュニア、ミドル、シニアのどれか。職種名か本文に書きます。

経験年数はレベルの大まかな目安にすぎず、しかも弱い目安です。上で触れた研究では、職務成績の予測力が最も低いものの一つに数えられています。経験年数を書く場合は、その年数で何ができるようになっているはずなのか、その仕事の内容も書きましょう。

### 3. 日々の業務内容

テストにとって最も役に立つのは業務内容の行です。「毎月の消費税申告書を作成する」や「報告されたバグを切り分けて再現する」と書けば、どの知識がどんな場面で使われるかが問題の作成者に伝わります。業務内容は、新しい同僚に仕事を説明するときのように、「何を」「どうする」の形で書きます。

ある職種で通常どんな仕事をするのかがわからない場合は、[O*NET OnLine](https://www.onetonline.org/) に、数百の職業について典型的なタスク、使う技術、必要な知識がまとめられています。チェックリストとして使い、自社のその職種が実際に行うことだけを残しましょう。

### 4. 必須と歓迎の明確な区別

歓迎要件まで確認するテストは、1 か月あれば教えられることで人をふるい落としてしまいます。入社初日から必要なスキルを決め、それ以外ははっきり区別して書くか、テストを作るテキストから外しておきます。

チームが入社後に教えるつもりの知識は、選考のテストにそもそも含めるべきではありません。統一ガイドラインも、内容の妥当性に基づくテストは「従業員が職務の中で習得することが期待される」知識には適さないとしています（[29 CFR 1607.14(C)(1)](https://www.law.cornell.edu/cfr/text/29/1607.14)）。

## 書かないほうがよいこと

求人広告には役立っても、テストには何の役にも立たない行があります。そもそも書くべきでない行もあります。

- **性格や姿勢を表す言葉：**「自走できる方」「ロックスター」「情熱のある方」など。知識を問う問題では確認できず、仕事ではなく人のタイプを表しているように読めがちです。
- **社風、福利厚生、スローガン。** 求人広告に残すのはかまいませんが、テストの材料にはなりません。
- **必須条件：** 資格・免許、就労資格、言語、勤務可能な時間など。書類選考で確認する「はい・いいえ」の条件であって、テストする知識ではありません。
- **特定の層の応募をためらわせる表現。** 米国の EEOC（雇用機会均等委員会）は、「女性」や「新卒」を求める広告を例に挙げ、それが「男性や 40 歳以上の人の応募をためらわせるおそれがある」とし、法律に違反する可能性があるとしています（[EEOC](https://www.eeoc.gov/prohibited-employment-policiespractices)）。EU と英国にも同様のルールがあります。思い描いている人物ではなく、仕事を書きましょう。
- **会社がしていることすべて。** その職種がまったく関わらない製品についての段落が、トピックになってしまうことがあります。

## 公開する求人広告とテストに使うテキストは別でよい

求人広告は仕事の魅力を伝える必要がありますが、テストに必要なのは要件だけです。求人広告が長くても、その全文からテストを作る必要はありません。要件と業務内容、それにレベルを書いた 1 行を貼り付け、残りは外しましょう。15 行の的確なテキストから作ったテストのほうが、3 ページのテキストから作ったテストより、たいていよいものになります。

## 例

**修正前：**

> データ分析が大好きな、経験 5 年以上のロックスター級データアナリストを募集しています。最高のチームの一員として、最新のツール（SQL、Python、BI ツールなど）を使ったワクワクするプロジェクトに携わっていただきます。高いコミュニケーション能力と成長意欲は必須です。ランチ無料、ペット同伴可のオフィスです！

これをもとに作るテストは、レベル、どの SQL か、どの BI ツールか、「ワクワクするプロジェクト」が何を含むのかを推測するしかありません。文章の半分はテストできない内容です。

**修正後：**

> **データアナリスト（ミドル）。** 定型的な分析は一人で行い、新しいモデルはシニアアナリストと一緒に作ります。
>
> - PostgreSQL で SQL を書く：結合、集計、ウィンドウ関数、遅いクエリの実行計画
> - 営業チーム向けの Power BI ダッシュボードを作成・管理する
> - Python と pandas でデータをクレンジングし、結合する
> - 指標を定義し、検証する：コンバージョン、リテンション、コホート分析
> - 分析結果を非エンジニアのマネージャーに、文書と短いミーティングで報告する
>
> 歓迎（テスト対象外）：dbt、EC 業界での経験。

どの行も問題で問えることを示しており、レベルが書かれ、歓迎要件も区別されています。

## テストを作る前のチェックリスト

- 各スキルが、性格ではなく、ツール、手法、概念を示している。
- レベルが書かれている：経験レベル、一人で決めること、扱うケースの難しさ。
- 業務内容が「何を」「どうする」の形で書かれている。
- 必須要件と歓迎要件がはっきり分かれている。
- 入社後に教えるつもりのことが含まれていない。
- 必須条件は書類選考に回している。
- 思い描く人物についての表現がなく、仕事についてだけ書かれている。

## prepza は求人票をどう使うか

prepza は、求人票から時間制限付きの選択式スキルテストを作るツールの一例です。上のアドバイスが実際にどう働くかがわかるよう、prepza がテキストをどう扱うかを紹介します。

- **すべての要件を読み取ります。** AI が、歓迎・尚可とされたものも含めてすべてのセクションから、スキル、ツール、概念、資格、日々の業務を一つずつ拾い出します。社風の説明、福利厚生、スローガンは除外されます。
- **置き換え可能な例は 1 つにまとめます。**「A、B などのツール」はツールの種類として扱い、テキストが優先しているもの（なければ最も広く使われているもの）を例にします。「と」でつながれた項目は別々のままです。ですから、特定のツールが 1 つ必要なら、そのツールだけを書いてください。
- **年数と性格は除外します。** 経験年数、経験レベル、意欲などの表現はテストできないので、それが指しているスキルだけを使います。
- **レベルはテキストから決まります。** 求人票が求める経験レベル、経験年数、責任の範囲から、テストのレベル（初級、中級、上級）が決まります。レベルによって問題の深さと 1 問あたりの初期時間が決まり、初級と中級は 60 秒、上級は 75 秒です（[スキルテストの時間設定](/guides/skills-test-timing-and-extra-time)を参照）。
- **問題が作られる前に、あなたがトピックを承認します。** 要件は最大 10 個のトピックになり、各トピックには最大 5 個のサブトピックが付きます。トピックのチェックを外す、名前を変える、サブトピックを編集する、変更内容を普通の文章で伝える（「dbt は外して」）ことができます。紛れ込んだ歓迎要件も、ここで簡単に外せます。
- **その後、各トピックに専用の問題バンクが作られ、** 各候補者にはそこからランダムな問題セットが出題されます。

貼り付けられるのは最大 10,000 文字です。職種を 1～2 行で説明するだけでもかまいません。レシピや雑談のように、テストできることが何も書かれていないテキストは受け付けられません。スキルの短いリストでも使えますが、レベルと日々の業務が書かれた求人票のほうが、よいトピックになります。

試すには、ホームページに求人票を貼り付けるか、[職種別のスキルテスト](/tests)から用意されたテストを選んで始めてください。
